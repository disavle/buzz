# Buzz — трекер энергетиков

Название: **Buzz** (утверждено 2026-10-15).

## Суть
Записываешь каждую выпитую банку энергетика за пару тапов. Приложение считает кофеин и сахар за день, предупреждает о превышении лимита (по умолчанию 400 мг кофеина в сутки) и показывает статистику на графиках Swift Charts. Работает офлайн, данные синхронизируются с собственным бэкендом на Vapor.

Что тренируем:
- **SwiftUI**: NavigationStack, TabView, LazyVGrid, sheet, формы, анимации кольца прогресса.
- **Observation**: `@Observable` модели экранов вместо ObservableObject.
- **SwiftData**: локальное хранение каталога и записей, `@Query`, фильтры по дате.
- **Swift Concurrency**: async/await для сети, actor для синхронизации, поиск с debounce через Task.
- **Swift Charts**: BarMark, LineMark, SectorMark, RuleMark для лимита.
- **Локализация**: String Catalog (`Localizable.xcstrings`), `LocalizedStringResource`, форматтеры единиц и дат.
- **Vapor**: REST API, Fluent + PostgreSQL (или SQLite для старта), простая авторизация по токену.

## Экраны (MVP)
1. **Сегодня** — кольцо «кофеин за день / лимит», сумма сахара, список выпитого сегодня, кнопка «+».
2. **Добавить** (sheet) — выбор напитка из каталога или недавних, объём, время (по умолчанию сейчас), цена (необязательно).
3. **Каталог** — сетка банок с поиском; можно добавить свой напиток (бренд, название, объём, кофеин на 100 мл, сахар).
4. **Статистика** (Swift Charts):
   - кофеин по дням за неделю/месяц (BarMark + RuleMark лимита);
   - во сколько обычно пьёшь (распределение по часам);
   - любимые бренды (SectorMark);
   - траты по неделям (LineMark).
5. **Настройки** — дневной лимит кофеина, вход/выход, ручная синхронизация.

## Языки
Приложение на **русском и английском** с первого дня.
- Клиент: все строки в String Catalog (`Localizable.xcstrings`), язык берётся из системы, плюс выбор языка в настройках приложения (через системные настройки iOS).
- Плюрализация через каталог («1 банка / 3 банки / 5 банок», «1 can / 3 cans»).
- Числа, мг, мл, валюта и даты — только через `FormatStyle` (`.formatted()`, `Measurement`), без ручной склейки строк.
- Swift Charts: подписи осей и легенд тоже из каталога.
- Бэкенд: коды ошибок в ответах (`"error": "limit_invalid"`), текст ошибки переводит клиент. Названия брендов и напитков не переводятся.

## Сущности
**Drink** — напиток из каталога
- `id: UUID`, `brand: String`, `name: String`
- `volumeMl: Int` (стандартный объём банки)
- `caffeinePer100ml: Double`, `sugarPer100ml: Double`
- `imageURL: URL?`, `isCustom: Bool`, `ownerId: UUID?` (для своих напитков)

**Entry** — выпитая банка
- `id: UUID`, `drinkId: UUID`, `consumedAt: Date`
- `volumeMl: Int`, `price: Decimal?`
- `caffeineMg`, `sugarG` — считаются при создании и хранятся, чтобы статистика не менялась при правке каталога
- `updatedAt: Date`, `deletedAt: Date?` (для синхронизации)

**User**
- `id: UUID`, `email: String`, `passwordHash: String`, `dailyCaffeineLimitMg: Int` (по умолчанию 400), `locale: String` (`ru`/`en`, на будущее для пушей)

## API (MVP)
| Метод | Путь | Что делает |
|---|---|---|
| POST | `/auth/register` | регистрация, возвращает токен |
| POST | `/auth/login` | вход, возвращает токен |
| GET | `/me` / PATCH `/me` | профиль и дневной лимит |
| GET | `/drinks?query=` | каталог: общий + свои, поиск |
| POST | `/drinks` | добавить свой напиток |
| GET | `/entries?from=&to=` | записи за период |
| POST | `/entries` | добавить запись (id генерирует клиент) |
| DELETE | `/entries/:id` | удалить (мягкое удаление) |
| GET | `/sync?since=` | всё изменённое после даты, для офлайн-синхронизации |
| GET | `/stats?period=week\|month` | агрегаты для графиков (по дням, часам, брендам) |

Статистику на старте можно считать и на клиенте из SwiftData; эндпоинт `/stats` — шаг для практики агрегаций во Fluent.

## Зачем синхронизация
Сервер — источник правды, а экран всегда читает из локальной SwiftData. Так приложение мгновенно открывается и работает без сети, а данные не пропадают при переустановке или смене телефона и видны на втором устройстве.

Как это выглядит для пользователя:
- Добавил банку — она сразу появилась в списке, с сетью или без.
- Пока запись не ушла на сервер, рядом маленький значок «не синхронизировано»; когда сеть есть, отправка идёт сама в фоне.
- Pull to refresh на «Сегодня» и в «Статистике»: сначала отправляет неотправленное, потом подтягивает свежее с сервера.
- Ничего локального не теряется при обновлении.

Как устроено:
- У каждой записи `syncState`: `synced` / `pending` / `pendingDelete`. Новые и изменённые записи становятся `pending` (по сути это очередь отправки, outbox).
- Синхронизация (actor `SyncEngine`): 1) отправить все `pending` (POST идемпотентен, id генерирует клиент, поэтому повтор не создаёт дублей); 2) `GET /sync?since=<последняя синхронизация>`; 3) применить ответ, но **не перезаписывать** записи, которые всё ещё `pending`.
- Когда запускается: при старте приложения, при возврате из фона, при появлении сети (`NWPathMonitor`), после добавления записи и по pull to refresh.
- Конфликт (одна запись изменена на двух устройствах): побеждает более свежий `updatedAt`.

Почему не «брать с бэка, а без сети хранить локально»: тогда при обновлении ответ сервера затрёт офлайн-правки, которых он ещё не видел. Очередь `pending` и правило «не трогать неотправленное» как раз это закрывают.

## Порядок работы
1. Клиент полностью офлайн: SwiftData, экраны «Сегодня», «Добавить», «Каталог» с захардкоженными напитками.
2. Статистика на Swift Charts по локальным данным.
3. Бэкенд: каталог и записи без авторизации.
4. Авторизация и синхронизация.

## Вне MVP
Виджет и Live Activity, напоминания, Apple Health (кофеин), сканер штрихкода банки.
